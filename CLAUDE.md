# FleetOS — project instructions

Operations control tower for autonomous (Tesla Cybercab) fleet owners. Plan: `docs/superpowers/plans/2026-09-26-fleetos-roadmap.md` · progress: `tasks/todo.md` · requirements: `docs/requirements/` · research evidence: `docs/research/`.

## Workflow
- **One task = one commit** that includes its ticked box in `tasks/todo.md`, **pushed straight to `main`** (trunk-based; Atharva follows progress there). No feature branches.
- The prototype in `prototype/` deploys to GitHub Pages only when files under `prototype/` (or the Pages workflow) change. Don't edit it unless the task is about the prototype; if you do, `pnpm prototype:build` must pass and the live site must be checked after deploy.
- Tooling: pnpm workspaces + Turborepo (`pnpm build|dev|lint|typecheck|test`); pnpm version is pinned in `package.json` (`corepack enable pnpm`).
- Before committing code, run the CI sequence (README → Checks). After any visual change, screenshot desktop + phone and look at them; stop dev servers by port (`kill $(lsof -tiTCP:3000 -sTCP:LISTEN)`).
- `apps/web` uses **Next.js 16**: read `apps/web/AGENTS.md` and the bundled docs in `node_modules/next/dist/docs/` before writing Next code (Turbopack default, `proxy` not `middleware`, async params, no `next lint`).
- Toolchain pins and why: TypeScript 6.0 (typescript-eslint needs < 6.1), ESLint 9 (Next's plugins don't support 10), pnpm 10 (corepack 0.34 can't run 12). See `tasks/lessons.md`.
- Local `pnpm dev` auto-signs-in `DEV_AUTO_LOGIN_EMAIL` (from `pnpm db:env`) via `/auth/dev-login`; it's inert outside `next dev`. Don't weaken that guard. E2E alongside dev: `PORT=3100`.
- After each task, append an entry to the Obsidian progress log (`claude_memory/projects/FleetOS/fleetos-progress-log.md`, via the `obsidian` CLI when the app is running).
- Record corrections in `tasks/lessons.md`.
- Before each build task, show Akshat a mental map (diagram) of what's being added and how it connects; after each task, explain what it achieved in product terms, not just files and test counts.

## Substitute data must be marked in code
Wherever code uses a **stand-in instead of the real source** (simulator data, a CSV import instead of an API, manual entry, an inferred estimate instead of a direct measurement, a static table instead of a live feed, or test fixtures used at runtime), put a `SUBSTITUTE` marker directly above it. The marker is how we find everything to replace when a real source arrives, so **no substitute ships without one**.

```ts
// SUBSTITUTE(<capability>, <kind>): <what this stands in for, in one line>
//   Real source: <API/feed that should replace it, or "none available as of YYYY-MM-DD">
//   Replace by: <the concrete change, e.g. "implement TeslaProvider.streamTelemetry and flip capability to live">
//   Docs: docs/requirements/data-sources.md §<section>
```

- Use `--` instead of `//` in SQL, `#` in YAML/shell. Keep the four lines; `Real source` and `Replace by` are required.
- **`<kind>`** is one of: `simulated` (generated by the simulator) · `csv` (file import instead of an API) · `manual` (user-entered instead of measured) · `inferred` (derived estimate instead of a direct signal) · `static` (fixed/published table instead of a live feed) · `fixture` (recorded sample data used outside tests).
- **`<capability>`** is `tesla` (simulator standing in for the Tesla Fleet API) or one of the preview capabilities: `rides`, `earnings`, `cabin_events`, `autonomy_events`, `dispatch`, `charger_telemetry`, `live_tariffs`, `vendor_tracking`. It must match the capability registry (`GET /api/v1/capabilities`). Add a new capability to the registry and to `data-sources.md` before using a new name.
- Mark the **seam** (the function, provider or query that produces the substitute), not every caller.
- `pnpm substitutes` (roadmap task 2.2) lists every marker and fails CI on malformed ones.

Example:

```ts
// SUBSTITUTE(charger_telemetry, inferred): charger occupancy = vehicles at the hub whose ChargeState is Charging.
//   Real source: OCPP 1.6J/2.0.1 StatusNotification from depot chargers (not available for Superchargers).
//   Replace by: ingest OCPP connector status into hub_chargers and read occupancy from it.
//   Docs: docs/requirements/data-sources.md §5
export function inferChargerOccupancy(vehicles: VehicleSnapshot[], hub: Hub): number { … }
```

## API rules
- Every `/api/v1` route is built with `apiRoute(op, handler)` (`apps/web/src/lib/api/handler.ts`) from an operation in `operations.ts`; the contract test fails if the route, its query params or its response schema drift from `docs/architecture/openapi.yaml`. Change the spec first, then the code.
- One `/api/v1`. Each operation is tagged `stable` or `preview`. Preview endpoints return simulated data in demo orgs and `501 capability_unavailable` elsewhere, **never `200` with empty data**. `/api/v2` is only for breaking changes to stable endpoints. See roadmap §3a.

## Tesla rules
- Never schedule `vehicle_data` polling or wake a car to read data; use Fleet Telemetry (≈ $4 vs ≈ $72 per car per month). `vehicle_data` is for backfill or explicit user requests only.
- Tokens and private keys live server-side (Supabase Vault), never in the browser. All server-side token calls go to `fleet-auth.prd.vn.cloud.tesla.com`.
- There's no Tesla sandbox: CI uses recorded fixtures; real-vehicle checks are manual and logged.
